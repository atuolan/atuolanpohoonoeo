新增審查結果（2026-08-17 11:25）
- UI 路徑審查已完成，與上述證據一致：8000 條會全量進 reactive；visibleMessages 仍全量 filter；visibleCount 每次 +100 且不回收；沒有 virtualization；MessageBubble 逐條跑 regex/HTML/marked。
- 生成路徑的資料邊界：ChatScreen.vue:3456-3472 先以 actualMessageCount 裁切 messagesToUse，PromptBuilder 再依 maxContextLength/token budget 裁切；因此「8000 條全部送 API」尚未證實。若 actualMessageCount=1000，生成端最多先看到該設定範圍，而 UI 仍保留全部 8000。
- PromptBuilder.ts:3182-3291 對 prompt history 逐條 await tokenCounter；tokenCounter 目前是 text.length/4 的輕量估算，但每條仍有 O(n) 迭代，replyTo 會對 messages.find。這是生成延遲放大因子，不足以單獨證明 renderer crash。
- ChatScreen.vue:4578-4595 僅在 backgroundGenerationEnabled 時對完整 apiMessages 做 JSON.stringify 並送遠端；是否造成閃退需以實際設定與 Performance trace 判斷。
- ChatScreen.vue:4642-4649 串流 token 會直接改最後一條 reactive 訊息；在可見列表已展開時，會重新觸發該 bubble 與 visibleMessages 依賴。這是 UI 根因假設的放大器，仍需 trace。
- ChatScreen.vue:5813-5818 每次生成 finally 都會 await saveChatImmediate；useChatPersistence.ts:67-78、100-129、174-177 會從完整 reactive messages 建快照、轉成可存格式、structuredClone chat，再全量保存。
- db/chatMessageStore.ts:47-88 的 saveChatMessages 會掃描該聊天既有 IDB cursor，並逐條 put incoming；因此高樓層生成結束時，保存路徑也可能產生長任務與記憶體峰值。

目前最精確的首要根因假設
- 已證實的觸發條件是「全量歷史 reactive + 無界可見 bubble + 每 bubble 字串解析」；這條鏈可解釋 8000 樓後 UI 卡頓與 renderer 記憶體壓力。
- 深層 watch、PromptBuilder、背景生成 JSON 序列化是額外放大器，尚未有 crash stack/trace 證明其中任何一項是唯一根因。
- 若 actualMessageCount 被設到 8000 或接近上限，PromptBuilder 的 `messages.find` 會讓 replyTo 密集的歷史出現 O(N^2) 風險；目前預設上限 1000，因此必須以實際設定確認。

使用者補充：已開啟「僅讀取幾樓」
- 這個設定只套用在 triggerAIResponse 的 `messagesToUse`，也就是送入 PromptBuilder/API 的歷史範圍（ChatScreen.vue:3454-3473）。
- 聊天載入仍由 `loadAndRepairChatMessages(chat)` 取得全部 IDB 訊息，再全部寫入 `messages.value`（ChatScreen.vue:7039-7084）；因此它不會降低初始 reactive 陣列、visibleMessages 全量掃描或向上展開 bubble 的成本。
- 在此設定已開啟的前提下，生成 prompt/JSON 的優先級下降；先做「不生成，只開啟並向上展開」的 UI 實驗，再單獨測試生成結束的全量保存。
