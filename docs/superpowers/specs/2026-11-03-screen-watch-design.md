# 設計：他看得到你在手機上做什麼（看螢幕模式）

> 狀態：設計中，第 0 步（iOS 可行性測試）進行中。**第 0 步要先過，才做後面的。**
> 2026-11-08 更新：開始的方式改成**像 DC 分享螢幕**——在 App 裡按按鈕就開始；寫上第 0 步目前的測試結果。

## 想要的效果

玩家在聊天裡按「分享螢幕」，**像在 DC 分享螢幕一樣**：跳出系統的「開始廣播」視窗（已經選好 203 Phone）→ 按開始，
然後切去用別的 App（滑 IG、看影片、打遊戲）。
角色每隔幾分鐘看一次畫面，用**系統通知**回應（「你又在滑貓咪影片了？」）。
回到 App 時，這段期間他說的話都已經在聊天紀錄裡。

不做「即時一直看」：那要很頻繁地送畫面（每 10 秒一張，一小時大約 360 張圖），費用太高。

## 為什麼不用 MCP

MCP 是讓 AI 呼叫外部工具的規格，跟截圖無關。App 本來就自己呼叫 AI 的 API，
缺的是**原生的截圖能力**，這要 iOS 和 Android 各寫原生程式。

## 關鍵限制：背景時網頁不會跑

玩家切去別的 App 後，我們的 App 會進背景。iOS 幾秒內就會暫停 App，Android 的 WebView 也可能被暫停。
所以**截圖、送 AI、發通知都要在原生那邊完成**，不能靠網頁（Vue）。

整體流程：

1. 玩家在聊天裡按「讓他看我的螢幕」
2. 網頁準備好一份「看螢幕包」交給原生：
   - API 網址、金鑰、模型（要用看得懂圖片的模型）
   - 角色名稱、人設重點、最近的總結、最近幾則聊天（壓成一段系統提示）
   - 間隔（例如 3、5、10 分鐘）、每次最多回幾句
3. 原生開始截圖，每隔一段時間：
   - 縮小圖片（寬 720 左右、JPEG），控制費用和記憶體
   - 送去 AI，附上看螢幕包
   - 用角色的名字發系統通知
   - 把截圖時間和回覆存進佇列
4. 玩家回到 App，網頁讀佇列，把回覆插進聊天紀錄（標成「看螢幕時說的」）

## iOS：螢幕廣播擴充元件（ReplayKit Broadcast Upload Extension）

- **跟 DC 用的是同一個東西**：iOS 要看到別的 App 的畫面，只有螢幕廣播擴充元件這條路（DC、LINE、Zoom 都是）
- 開始的方式（像 DC）：聊天裡按「分享螢幕」→ App 用 `RPSystemBroadcastPickerView`（`preferredExtension` 設成我們的擴充元件）
  跳出系統的「開始廣播」視窗 → 玩家按開始。從控制中心長按「螢幕錄影」→ 選「203 Phone」也可以
- 上方會一直有紅色錄影標示（系統規定，拿不掉）
- 廣播期間，**擴充元件**（跟 App 分開的小程式）會一直收到畫面；它自己抽樣、送 AI、發通知
- 擴充元件記憶體上限很低（大約 50MB），所以每次只留一張縮小的圖，不能累積
- **跟 DC 一樣，擴充元件自己連網路**：DC 的擴充元件把畫面直接送到 DC 的伺服器；我們的擴充元件把縮圖直接送去玩家設定的 AI。
  App 在背景會被暫停，所以不能靠 App 轉送
- 擴充元件和 App 只在兩個地方要交換資料，用 **App Group**：
  - 開始時：App 把「看螢幕包」交給擴充元件（API、金鑰、角色提示）
  - 結束後：擴充元件把回覆佇列交回 App，寫回聊天
- App Group 的名字要在執行時從簽名讀（見下面「第 0 步目前的結果」），不能寫死

### ⚠️ 風險：自簽安裝

目前 iOS 版是 GitHub Actions 打出**沒簽名的 IPA**，玩家用 **Sideloadly＋自己的 Apple ID** 簽名安裝。
以下幾點**不確定**，要實測：

1. Sideloadly 簽名時，會不會一起簽好擴充元件（`.appex`）
2. 免費 Apple ID 能不能用 App Group；如果不行，擴充元件和 App 拿不到同一份資料
3. 多一個擴充元件會多用一個 App ID，免費帳號 7 天內能建的 App ID 有限

如果 App Group 不能用，備案：擴充元件只做「截圖＋送 AI＋發通知」，看螢幕包在開始前透過別的方式傳過去（要再研究），回覆只出現在通知裡，不寫回聊天。

| 1 | 擴充元件有打包進 IPA | ✅ |
| 2 | Sideloadly 裝完後出現在螢幕錄影選單 | ✅（換新版後有時要**重開機**才會出現、才選得到） |
| 3 | 廣播中能發通知 | ✅ 每 30 秒都有發，發送結果「成功」。之前沒跳出來是手機開著**勿擾模式**，通知都收在「勿擾模式期間」 |
| 4 | 能處理畫面、記憶體夠用 | ✅ 跑了 3 分鐘以上沒被系統關掉：30 秒收到 1366～1600 張（系統一直丟畫面，收到就丟，不花 token），縮圖 76～188 KB |
| 5 | App 和擴充元件共用資料（App Group） | ✅ 兩個方向都通：擴充元件讀到 App 寫的值，App 也讀到擴充元件寫的次數和發通知結果 |
| — | 在 App 裡開始分享（像 DC） | 看起來可以（App 開啟後 11 秒擴充元件就開始了），待玩家確認是不是用按鈕開始的 |

查到的事：

- **Sideloadly 會把 App Group 改名**：原本的 `group.uk.aguacloud.aguaphone` 變成 5 個 `group.<代碼>.1`～`.5`，
  簽名裡的順序是亂的。寫死名字的話，`UserDefaults(suiteName:)` 不會報錯，只會偷偷用各自私有的儲存，兩邊永遠讀不到對方
- 做法：從自己執行檔的簽名讀出實際的 App Group，用 `containerURL` 確認打得開；App 和擴充元件都**寫進全部、從全部讀**
- **第 0 步通過**（第 11 次打包，2026-11-08）：可以照設計做完整版
- 教學頁要提醒：開著勿擾／專注模式時，角色的通知不會跳出來，會收在通知中心

### 熱更新沒用

這是原生程式，**Capgo 熱更新送不過去**。玩家要重新下載 IPA、重新用 Sideloadly 安裝。

## Android：螢幕擷取（MediaProjection）＋前景服務

- 玩家按開始 → 系統跳出「要開始分享螢幕嗎？」→ 允許
- 開一個**前景服務**，通知列會一直顯示「正在讓 ○○ 看你的螢幕」（系統規定）
- 服務裡定時抓一張畫面 → 縮小 → 送 AI → 發通知 → 存佇列
- Android 14 以後每次開始都要重新允許，這是系統規定
- 一樣要重新裝 APK，熱更新送不過去

## 兩邊共用

- **網頁那邊**只做一份：準備看螢幕包、設定頁、讀佇列寫回聊天
- **Capacitor 外掛介面**兩邊一樣：`start(pack)`、`stop()`、`readQueue()`、`clearQueue()`
  - iOS 的 `start(pack)`：把看螢幕包寫進 App Group，再跳出系統的「開始廣播」視窗（像 DC）
- **AI 請求格式**用 OpenAI 相容格式加圖片，原生兩邊各寫一次

## 費用和隱私

- 每張截圖都是一次看圖的 API 費用。設定頁要寫清楚，預設間隔 5 分鐘、可以調
- 加「單次最長時間」（例如 1 小時自動停），免得忘記關
- **暫停按鈕**放在通知上
- Android 可以設「這些 App 不截圖」（銀行、密碼管理）。iOS 擴充元件看不到現在是哪個 App，做不到，要在說明裡提醒
- 截圖只送給玩家自己設定的 API，不存檔、不上傳到別的地方

## 步驟

0. **可行性測試（iOS，最先做）**：做一個最小的廣播擴充元件，只做「每 30 秒發一則『我看到了』通知」。
   用 GitHub Actions 打包 → 你用 Sideloadly 安裝 → 確認：
   - 擴充元件有出現在「螢幕錄影」的選單裡
   - 開始廣播後有收到通知
   - App Group 能不能讀寫
   **這步過了才做下面的。** 我在雲端環境沒辦法編譯或執行 iOS，只能寫好程式交給 GitHub Actions 打包，要靠你在 iPhone 上測。
1. 網頁：看螢幕包、設定頁、佇列寫回聊天（兩邊共用，可以先寫好並測試）
2. iOS：擴充元件抽樣、縮圖、送 AI、發通知、寫佇列
3. Android：MediaProjection＋前景服務，做一樣的事
4. 加上暫停、自動停止、略過 App（Android）
5. 教學頁：按「分享螢幕」後在系統視窗按開始（iOS，也可以從控制中心）、權限說明（Android）
